# 单一报警查询接口与后端接入

首版新增一个只读接口 `GET /api/alarms`。工控机记录各模块的故障、重复发生和恢复事件；业务后端统一同步后，按 `category`、`severity` 和设备分类展示。后端确认、备注、通知与历史查询属于业务后端自己的数据，不回写工控机。

业务后端的逐步接入、字段处理、入库事务、轮询与恢复示例见 [业务后端接入指南](alarm-backend-integration.md)。

报警查询不清除报警，不确认报警，不复位设备，不触发 SDK/电机探测。后端停止轮询不会新增停产逻辑；现有任务控制和设备保护保持原有行为。硬件急停、自动停产、人工复位和无人值守安全闭环不由这个只读接口实现。

## 1. 启用与部署

| 环境变量 | 含义 |
| --- | --- |
| `COLONY_ALARM_DB` | 本地 SQLite 文件，默认 `data/alarms.sqlite3`。服务账户需要目录及文件读写权限。 |
| `COLONY_DEVICE_ID` | 稳定设备标识。未设置时生成并持久化一个标识；正式部署建议显式分配。 |
| `COLONY_ALARM_TOKEN` | 报警接口的只读 Bearer 凭证。未配置返回 `503 ALARM_AUTH_NOT_CONFIGURED`；不正确的凭证返回 `401`。 |
| `COLONY_ALARM_DISK_WARNING_PERCENT` | 剩余空间告警比例，默认 `20`。 |
| `COLONY_ALARM_DISK_CRITICAL_PERCENT` | 剩余空间严重告警比例，默认 `10`。只上报，不改变任务控制。 |

磁盘阈值必须满足 `0 < critical < warning < 100`。填反、非数字或非有限值等非法配置会使两个阈值一起回退为 `20` / `10`，报警记录与查询继续工作，同时产生 `ALARM_DISK_CONFIG_INVALID`（P2）。`monitoring.disk` 返回实际使用的 `warning_percent`、`critical_percent` 和 `thresholds_defaulted`；修正环境变量并重启服务后，该配置报警自动恢复。

凭证通过服务环境文件或现有秘密管理方式注入，限制文件读取权限，不提交到仓库，也不放进 URL。业务后端使用 `Authorization: Bearer <token>`。这项凭证只保护报警查询，不能替代现有控制接口的网络隔离和授权。

生产环境在受控网络中使用 HTTPS，通常由已有网关终止 TLS。下面是可合并进已有 Nginx 配置的示意；证书、域名和后端地址应按现场配置。

```nginx
server {
    listen 443 ssl;
    server_name colony-device.example.internal;
    ssl_certificate     /etc/nginx/tls/device.crt;
    ssl_certificate_key /etc/nginx/tls/device.key;

    location = /api/alarms {
        limit_except GET { deny all; }
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Authorization $http_authorization;
        proxy_set_header Host $host;
        proxy_read_timeout 5s;
    }
}
```

同时由主机防火墙限制 API 原始端口，避免绕过网关。不要记录 Authorization 请求头。后端需信任设备证书的签发 CA；示例客户端不关闭证书验证，也不携带凭证跟随重定向。

SQLite 状态与事件写入同一事务，正常进程重启保留 `stream_id` 和序号，`boot_id` 每次进程启动改变。重建数据库会产生新的流。**恢复旧备份前应停止服务，恢复后执行流标识轮换，再启动服务**，避免旧序号被后端误认为已经消费：

```bash
python -m workflow.alarm_maintenance rotate-stream --database /opt/colony_system/data/alarms.sqlite3
```

## 2. 请求与响应契约

轮询响应、全部 51 个公开代码、错误响应与恢复生产说明见 [报警完整示例](alarm-examples.md)，可供接入参考的 JSON 见 [场景示例文件](examples/alarm-polling.json)。

```http
GET /api/alarms?mode=events&limit=100
Authorization: Bearer <token>
```

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `mode` | `events` | `events` 获取事件增量；`snapshot` 获取当前未恢复故障的冻结快照。 |
| `cursor` | 不传 | 服务端返回的不透明游标。后端原样保存、原样传回，不解码、拼接或用时间戳代替。 |
| `limit` | `100` | 每页条数，范围 `1..500`。 |

首版不支持类型筛选。**每台设备维护一套事件消费位置**，成功保存一页后再推进位置；展示层可以任意按类型、严重程度和任务筛选。全类型同步仍然是分页、增量同步，不是每次重读全部历史。

通用响应字段：

| 字段 | 含义 |
| --- | --- |
| `protocol_version` | 当前为 `1`，不支持的版本应停止推进游标并提示契约不兼容。 |
| `device_id` | 稳定设备标识；后端不能把另一设备的响应写入本设备消费状态。 |
| `stream_id` | 持久化事件流标识；变化后必须重新同步。 |
| `boot_id` | 本次 API 进程启动标识，不等于硬件已恢复。 |
| `items` | 本页事件或快照记录。 |
| `next_cursor` | 下一页/下一次事件轮询使用的游标；快照末页可以为空。 |
| `has_more` | 为 `true` 时立即拉下一页，不等待下一轮 5 秒周期。 |
| `watermark` | 事件页的上界序号，或整份快照固定的上界序号。 |
| `retention_start_sequence` | 当前仍可获取的历史起点，用来说明保留范围。 |
| `events_cursor` | 快照上界对应的事件游标；快照模式提供。首次接入仍需回放保留历史，不能直接从这个游标开始而遗漏已恢复事件。 |
| `monitoring` | 本地记录器、监测线程、任务运行器等监测摘要及采样新鲜度。即使没有新事件，也要更新后端缓存。 |

单条事件示意，公开信息不包含原始异常、堆栈、SDK 文本或本机绝对路径：

```json
{
  "event_id": "event-opaque-id",
  "alarm_id": "alarm-opaque-id",
  "sequence": 101,
  "category": "camera",
  "code": "CAMERA_WORKER_FAILED",
  "severity": "P1",
  "transition": "occurred",
  "occurred_at": "2026-11-03T03:00:00+00:00",
  "recorded_at": "2026-11-03T03:00:00+00:00",
  "message": "相机工作进程异常，采集能力尚未验证恢复",
  "component": "camera",
  "resource": "default",
  "active": true,
  "count": 1,
  "task_id": "task-123",
  "execution_id": "execution-opaque-id",
  "diagnostic_id": "diagnostic-opaque-id"
}
```

以上标识与文案仅用于解释结构，实际 `code` 和文案由服务端目录提供。未知代码按通用故障展示，不能因为前端枚举未更新就丢弃整页。任务再次使用相同 `task_id` 时会得到新的 `execution_id`，后端据此区分两次执行。

`occurred_at` 表示故障发生时间，补录任务历史时取任务结束时间；`recorded_at` 表示进入报警数据库的时间。保留期按记录时间计算，消费顺序只按 `sequence`。`diagnostic_id` 用于检索本地日志；未处理的 HTTP 异常使用同一次请求的请求编号作为诊断编号。

报警目录分别位于 [设备报警](../workflow/alarm_device_codes.py)、[任务/视觉/存储报警](../workflow/alarm_task_codes.py) 和 [记录器自身报警](../workflow/alarm_service.py)。采集覆盖相机 SDK、进程与帧停滞、录像产物、运动通信/到位/限位/停止、物镜与交接、任务失败/中断、视觉故障与降级、补偿偏差、运行配置、文件读写和磁盘容量。正常任务取消、录像结束和往复运动流程结束以 `INFO` 历史事件保存。

| `transition` | 含义 |
| --- | --- |
| `occurred` | 持续性故障开始，`active=true`。 |
| `updated` | 同一故障再次发生或更新；同一 `alarm_id`，计数/最近发生时间更新。 |
| `recovered` | 通过实际能力成功证据确认恢复，`active=false`。 |
| `recorded` | 不可逆的历史事实，例如一次任务失败、中断或正常取消，`active=false`。 |

持续性故障按设备、组件、资源和代码归并。任务失败是已经发生的事实，之后另一次任务成功不会删除这条历史。相机进程重建本身不代表设备恢复；未观察到或过期的设备状态应呈现“未知”，不能从“无活动报警”推断健康。

| 严重程度 | 展示建议 |
| --- | --- |
| `P0` | 停止失败、运动状态不确定等已观察到的安全问题，置顶红色提示。 |
| `P1` | 任务失败、关键能力不可用，需要处理。 |
| `P2` | 可恢复异常、降级、容量不足等提示。 |
| `INFO` | 正常取消等历史事件，不作为生产故障通知。 |

普通参数校验失败、正常硬件占用冲突及合法的零菌落结果不作为生产报警。严重程度只控制信息呈现，不新增运动控制动作。

## 3. 首次接入、增量轮询和重新同步

推荐单设备单同步循环，默认每 5 秒发起一轮，单请求超时 3 秒，不重叠执行。

1. **首次接入**：不传游标获取 `snapshot`，立即拉完所有页。整份快照使用相同 `stream_id`、`watermark` 和 `events_cursor`；只在完整成功后一次性应用，不能收到第一页就清空后端现有报警。
2. **回放历史**：不传游标获取 `events`，从最早保留事件开始，把已经恢复的故障也写入历史。序号不大于快照 `watermark` 的历史事件不得覆盖快照当前状态。后端必须持久化快照上界；如果首个事件页的 `retention_start_sequence > 快照 watermark + 1`，说明快照提交后到首次回放之间已有事件过期，应记录缺口并重新获取快照。后端在这两步之间重启时也必须检查，避免遗漏已过期的恢复事件。
3. **推进游标**：同一数据库事务里保存事件、按 `event_id` 去重、更新当前状态并保存 `next_cursor`。事务失败时全部回滚，下轮仍从上次提交的游标重试。
4. **追赶积压**：`has_more=true` 时立即继续取下一页。没有更多数据后，再等待下一轮周期；空事件页也要保存有效游标、更新监测摘要。
5. **恢复同步**：HTTP `410` 或流标识变化时，记录历史缺口，重新完整获取快照并回放保留历史。保留原先已知报警，直到完整快照替换成功。快照只能清除序号不高于其 `watermark` 的旧状态。

快照最长有效 10 分钟；服务重启或快照缓存淘汰也可能使游标失效。过期后从首个快照请求重新开始，不把不同版本的分页拼在一起。历史事件保留 30 天，未恢复故障的当前状态不随历史清理。保留期之外的历史无法由这个接口补回，后端需要独立保存其历史。

HTTP 状态与处理：

| 状态 | 含义与后端动作 |
| --- | --- |
| `200` | 查询成功，包括存在 P0 报警的情况。处理事件和摘要。 |
| `400` / `422` | 参数、游标或契约使用错误，停止推进位置并修正调用。 |
| `401` / `403` | 凭证或权限错误，保留现有报警并显示接入故障。 |
| `410` | 游标已超过保留范围、快照过期或流变化。按响应原因重新同步，标注历史缺口。 |
| `503` | 报警存储不可读/未就绪或凭证未配置。绝不能当作“没有报警”。 |
| 其他错误、超时或不合法响应 | 保留消费位置和已知状态，记录本次同步错误并重试。 |

`410` 响应提供 `detail.error_code`、`message`、`resync_reason`、当前 `stream_id` 和可用历史起点。快照自身过期只说明这份快照应重取，不必推断出现了历史丢失。

超过 60 秒没有收到有效报警响应时，由**业务后端**产生“报警服务不可用/设备通信异常”。区分网络、鉴权、503 和契约错误，显示最后成功时间与最后已知状态。这个报警不能证明工控机断电、程序完全停止或电机已停止；设备无法通过一个已经失联的接口报告自己的失联。

后端“人工已确认”与设备“故障已恢复”是两个不同字段。确认仅关闭通知或记录处置人/备注，不篡改设备恢复状态。业务看板本身也需要现有运维监控，避免无人查看时通知链路失效。

## 4. 可运行的后端参考实现

[`tools/poll_alarms.py`](../tools/poll_alarms.py) 仅使用 Python 标准库；它演示一个设备对应一个 SQLite 消费库，真实业务后端应把相同事务边界接入自己的数据库与调度器。

```bash
export COLONY_ALARM_TOKEN='<通过受控方式注入实际凭证>'
python tools/poll_alarms.py \
  --url https://colony-device.example.internal \
  --database /var/lib/business-backend/device-001-alarms.sqlite3
```

`--once` 完成一轮后退出；`--interval` 默认 5 秒。只在受控本机联调时使用 `--allow-http --url http://127.0.0.1:8000`。示例不会发送 POST、确认、复位或控制请求。

| 本地表 | 用途 |
| --- | --- |
| `events` | 保留事件历史，以设备、流和事件 ID 去重。 |
| `alarm_state` | 当前状态投影；展示活动故障时使用 `active=1`，正文在 `payload`。 |
| `metadata` | 消费游标、设备/流标识、采样摘要、最近成功时间。 |
| `history_gaps` | 因保留期或流变化触发的重新同步记录。 |

`AlarmPoller.health()` 返回后端产生的通信报警及错误分类。示例进程每轮打印摘要，由业务后端接入看板；未替现有后端实现通知渠道、人工确认页面或值班机制。示例本地数据库写入失败时退出并保留旧事务，生产部署应由现有进程监管和监控报告此故障。

## 5. 可靠性边界与验收

设备报警（运动、Modbus、相机、物镜、交接与补偿）先提交到容量为 4096 的内存队列，再由独立 `alarm-writer` 线程按提交顺序持久化。设备线程不等待报警数据库、报警写锁或报警日志 I/O，因此故障后的停止命令不依赖报警落库完成。提交时保留任务上下文与发生时间；查询只返回已落库事件，不等待队列清空，刚提交的报警可能在下一轮轮询中出现。任务终态对账仍采用同步持久化结果判断，避免把“已入队”误认为“已保存”。

队列满、写入线程不可用或设备报警提交失败时，不回退到设备线程同步写入。`monitoring.store.pending_device_events` 表示等待处理的队列项数（不含正在写入项），`dropped_device_events` 表示本进程丢弃的设备事件数；丢弃会使记录健康状态降级，由监测线程补记 `ALARM_RECORDING_INTERRUPTED`。`device_writer_status` 返回 `not_started`、`running`、`failed` 或 `stopped`，写入线程失败时，即使数据库探测成功也仍显示降级。服务退出时先完成设备清理，再停止接收并等待队列排空，最多等待 2 秒；超过期限记录本地错误。内存队列尚未落库的事件在进程崩溃、断电或退出超时时可能丢失，不能视为已持久化。

自动化验证覆盖见 [报警接口验收记录](alarm-acceptance.md)。

本地报警写入失败不能覆盖原始业务异常或改变现有控制流程。记录器恢复后补记记录中断事实；任务失败/中断可以从任务 JSON 对账补录，但 JSON 与报警 SQLite 不在同一事务中，记录中断期间的瞬时硬件故障不保证全部补回。公开响应通过固定代码与文案输出，详细异常留在内部日志并用诊断标识关联。

上线前在实际网络、存储和硬件环境执行：

- 两次轮询之间故障发生并恢复，历史仍应包含两条事件；重复拉取不产生重复业务记录。
- 后端重启从已提交游标继续；提交失败不推进游标；分页积压能连续追赶。
- 快照分页期间并发发生/恢复故障，不提前清空当前状态，不让旧事件覆盖新状态。
- 事件过期或数据库重建明确触发重新同步与缺口记录；存储不可读返回 503，不返回空健康。
- HTTP 仍能响应但任务运行器停止时，摘要/事件能显示运行器故障；SDK 阻塞不阻塞报警查询。
- 停止后端轮询不会改变生产控制；连续失联超过 60 秒在后端显示通信故障，恢复后补齐积压。
- 正常网络且无积压时，从工控机记录事件到业务看板显示以 10 秒内为验收目标。自动化测试验证协议与消费行为，不能代替现场时延和硬件安全验收。

协议设计参考：[不透明分页令牌](https://google.aip.dev/158)、[报警应关注可行动症状及监测链路自身](https://prometheus.io/docs/practices/alerting/)。
